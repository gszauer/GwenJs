## 2026-04-29 — Dark skin + runtime theme switching

New top-level feature: skins are themable at runtime. Two stock palettes ship — `LIGHT_PALETTE` (the existing Windows-XP / silver theme, default) and `DARK_PALETTE` (a VS Code-ish dark theme). Calling `skin.setTheme(palette)` re-paints the 512×512 atlas in place, re-uploads to the GPU keeping the same `WebGLTexture` handle, and rebuilds `skin.colors` — every existing control picks up new colours on next render without reconstruction.

**Plumbing.**

- `src/skin/AtlasRegions.ts`: extracted the frozen `PALETTE` constant into a `Palette` interface plus two named exports (`LIGHT_PALETTE` / `DARK_PALETTE`); `PALETTE` is kept as an alias to LIGHT for back-compat. The two BAKED palette strips (the on-atlas pixels GWEN tooling reads via `pixelColour`) became `bakedRow500(p)` / `bakedRow508(p)` factories so they can be regenerated for whichever palette is active.
- `src/skin/DynamicSkin.ts`: introduced a module-level mutable `activePalette` (and matching `activeRow500` / `activeRow508`) that all 122 paint helpers reference. Replaced `PALETTE.X` with `activePalette.X` mechanically. Split `init()` into a private `paint()` method; both `init` and `setTheme` call it. `setTheme(palette)` swaps `activePalette`, re-paints the offscreen canvas, re-uploads via `loadTextureFromSource` (the same `Texture` slot — handle stable), and rebuilds the `colors` struct. Pre-`init` calls to `setTheme` defer painting; `init()` picks up the queued palette.
- `src/skin/Skin.ts`: `setTheme(palette)` / `getPalette()` delegate to `dynamicSkin`. Switched the one direct `PALETTE.menuStripBg` reference (in `drawMenuStrip`) to read `dynamicSkin.getPalette().menuStripBg` so the strip re-tones live.

**Text colours track the theme automatically.** `Text` got a `_colorIsExplicit` flag; render reads `skin.colors.label.default` when the flag is false, the explicit `_color` otherwise. `TextBox` no longer sets a hardcoded `#323232` in its constructor — same path makes it auto-flip in dark mode. Controls that already used `skin.colors.X` (Tree, Properties, etc.) needed no change.

**Atlas region tweaks.** `Tab.HeaderBar` previously hardcoded `#e8e8e8` / `#cfcfcf` for its gradient — now reads `tabActiveTop` / `tabActiveBot` from the active palette. `Input.ListBox.OddLine` zebra stripe was a hardcoded `#f4f4f4` — now `panelBright` so it darkens correctly.

**Demo: Help → Skin submenu.** Two checkable items (`Light`, `Dark`) under a new `Skin` entry in the Help menu, with the icon-margin gutter showing a check on the active theme. Clicking switches the palette + updates the canvas background via a small palette→Color helper. Output log records the change.

**Tests.** `tests/skin-theme.spec.ts` — 7 cases: API exports + default, `setTheme` reflects on `getPalette` + `colors`, texture handle stability, idempotent same-palette, pre-init deferred paint, render-after-switch doesn't throw, baked-row content differs across palettes. **Full suite: 1708/1708 green** (1694 prior + 14 new × 2 projects).

## 2026-04-28 (later) — Right-click context menus

New top-level feature: every control can attach a context menu shown on right-click.

**API.** Two methods on `Base`:

- `setContextMenu(menu)` / `getContextMenu()` — attach a `Menu` to a control. The field is typed as `Base | null` to avoid a `Base ↔ Menu` runtime import cycle (Menu already imports Base); Canvas narrows back to `Menu` via `instanceof` before opening.
- `onContextMenuRequest(x, y): Base | null` — virtual hook called on each right-click. Default returns the menu set above; override to build menus dynamically (e.g. a viewport that includes the click position in its commands) or to defer to a parent by returning `null`.

**Bubble rule.** When the user right-clicks, `Canvas.tryShowContextMenu` walks from the hovered control up through every parent calling `onContextMenuRequest`; the first non-null `Menu` wins and opens at the cursor. The walk fires *before* the "no specific control was hovered" early-return so a `canvas.setContextMenu(global)` produces a true app-wide fallback that fires on empty-area right-clicks too. The walk halts on `isMenuComponent` so right-clicking inside an already-open menu doesn't summon another. Auto-reparents the menu onto the canvas so it always draws on top regardless of where it was originally created.

**Demo.** New `Non-Standard → RightClick` entry showing all four configurations: panel-level "global" with submenus + accelerators + dividers, a button with its own override, a Label that builds a fresh menu per click via `onContextMenuRequest` (including the click coordinates in its items), and a Label that returns `null` from its hook to defer to the panel — proves the bubble rule.

**Tests.** Eight cases in `context-menu.spec.ts`: round-trip API, basic right-click open at cursor, child→parent bubbling, canvas-level fallback, dynamic hook returning a menu, null hook deferring up the chain, auto-reparenting onto canvas, no-menu pass-through. Full suite: **1694/1694 green**.

## 2026-04-28 (later) — ActionBar: tighten separator in multi-column mode

Bug: in two-column tool palettes, each separator left an empty grid row after it. Cause: layout advanced by `cells += cols` after placing a separator (one full slot row of 28 px) even though the separator itself only takes 8 px. Switched the multi-column layout from cell-index math to direct Y tracking — items advance Y by the slot height; separators advance Y by their own 8 px height. ## 2026-04-28 (later) — Docking: single-tab drag = whole-dock drag

User noticed a subtle difference between dragging a tab and dragging the strip's empty area when a docked panel has only one tab — the tab fired `TabButtonMove` while the empty area fired `TabWindowMove`. Same end result for the user, but different package names produced inconsistent intermediate state and broke an invariant for any future drop target that distinguishes the two. With 2+ tabs the conventional single-tab drag still applies. The check is duck-typed via the strip's existing `showsAsHeader()` method to avoid a circular import between `TabButton` and `DockedTabControl`. New regression test (`dock-base.spec.ts` #23) drives both the lone-tab and multi-tab cases. Full suite: **1676/1676 green**.

## 2026-04-28 (later) — Docking bug sweep (re-dock + re-attach correctness)

User reported "the newly docked control looks like it has no contents until I dock it elsewhere." Tracing through the re-host flow surfaced **three** related bugs in `TabControl` / `DockedTabControl` / `DockBase`, each of which independently turned a re-docked panel into a visible regression:

1. **`TabControl.onTabPressed` hid pages that had been reparented to another TC.** When `attachTabButton` fires its source-side cleanup — `sourceTC.onTabPressedExt(remaining[0])` — to clear a stale `_currentButton`, the old current's page has *already moved* to the destination's inner panel. The unconditional `oldPage.hide()` then hid it in the new dock, making the destination look empty until the page was reparented again. **Fix:** gate the hide on `oldPage.parent === this._inner`.

2. **Stale `onPress` subscriptions lingered after re-attach.** Each `attachTabButton` adds a new `btn.onPress.on(() => this.handleTabPress(btn))` bound to the new TC, but never removes earlier ones (the disposer model has no remove-by-target). When a tab moved A → B and the user clicked it in B, the A-side subscription also fired — and with bug #1 fixed, A's `onTabPressed` would still mutate A's own `_currentButton` and hide *one of A's local pages*. **Fix:** added a `btn.parent !== this._tabStrip` short-circuit at the top of `onTabPressed`. Stale subscriptions become no-ops; only the live TC's handler runs.

3. **Drag-attach left the dragged tab inactive in target.** Both `DockBase.attachTabButtonTo` (single-tab `TabButtonMove`) and `DockedTabControl.attachTabButton` only auto-pressed the incoming button when the target had no live current, so dragging a tab into a populated dock left it sitting hidden behind whichever tab was already active — directly contradicting the user's drag intent. **Fix:** unconditionally press the incoming button on every attach. To preserve `TabWindowMove` (whole-dock drag) semantics, `DockedTabControl.moveTabsTo` now snapshots the source's current selection before its per-tab loop and re-presses it in the target after, so the visible tab survives a multi-tab move.

Three new regression tests in `dock-base.spec.ts` cover the scenarios end-to-end (#19 single-tab drag from a multi-tab dock keeps moved page visible; #20 TabWindowMove preserves source's current; #21 single-tab drop onto a populated dock promotes the dragged tab; #22 clicking a moved tab doesn't corrupt the previous TC's state). Full suite: **1644/1644 green**.

## 2026-04-28 (later) — Tooltip rendering fixed (offset + size)

Two bugs working together had reduced tooltips to a stray glyph fragment near the cursor:

1. **`Canvas.renderToolTip` painted the background at world (0, 0).** `skin.drawToolTip(tip)` calls `drawBordered('Tooltip', tip.getRenderBounds())`, and `getRenderBounds()` is always `(0, 0, w, h)` (renderBounds are local). The renderer's offset at that point was still `(0, 0)` from the canvas-level setup, so the 9-slice frame painted at the canvas origin (visible behind the menu strip in the bug screenshot), while only `tip.doRender(this.skin)` — which calls `addRenderOffset(tip._bounds)` internally — moved the text to the cursor. Fix: temporarily shift the renderer offset to `(savedOffset.x + tx, savedOffset.y + ty)` around the `drawToolTip` call, then restore before `tip.doRender` so its own offset add still resolves correctly.

2. **`Label.setToolTip` sized the tip while it was still parentless.** `tip.sizeToContents()` was called before `setToolTipControl(tip)` reparented it onto the button. With no parent, `_text.refreshSize()` early-returns (it can't reach a skin via the ancestor chain to resolve the default font), leaving the inner Text at the default 10×10. The Label sized to that — `(20, 16)` after padding — which shrinkwrapped the tooltip to a tiny stub that only fit a single character (the "T" the user observed). Fix: parent first, then `sizeToContents()`.

Visual confirms the fix: "This is a tooltip" now renders fully framed at the cursor. Full suite still 1636/1636 green.

## 2026-04-28 (later) — FilePicker dialog hardened against silent failures

**Attach the `<input>` to the DOM, swallow exceptions in onPress.** A user reported `Browse…` on the FilePicker demo doing nothing in their browser, with a follow-on symptom that the ImagePanel demo's picker stopped responding too once the FilePicker section had been touched. The reproducible end-to-end click→filechooser→setFile pipeline runs cleanly in headed and headless Chromium via Playwright (1636/1636 tests green; visual screenshots confirm), so the failure is environment-specific. Two defensive measures applied to make the picker robust against the suspect failure mode (browsers that silently no-op `.click()` on a detached input — older Safari, some iOS WebViews, certain user-agent overrides):

1. The synthesized `<input type="file">` is now appended to `document.body` (positioned `fixed` off-screen at `-10000px,-10000px`, `pointer-events:none`, `opacity:0`) for the lifetime of the dialog and removed once the Promise settles via `change` or `oncancel`. Eliminates the detached-input footgun.
2. The Browse… `onPress` handler now wraps `openDialog()` in a `try`/`catch` plus `.catch(() => {})` on the promise, and `input.click()` itself is wrapped in `try`/`catch` that resolves with `null` on failure. Without this, a synchronous throw inside the `onPress` chain would propagate up through `Button.onMouseClickLeft` and skip the `canvas.mouseFocus = null` line — which would have routed every subsequent canvas click back to the original Browse button until the next layout pass cleared it. That's the most plausible source of the "after FilePicker, ImagePanel also breaks" cross-contamination the user described.

The standalone test for the click→filechooser flow (file-picker.spec.ts test #9) continues to pass, confirming the happy path still works. **Bundle: 201.0 KB raw / 48.8 KB gzip.**

## 2026-04-27 — Keyboard-nav overhaul + Properties grid rebuilt against GWEN

**Tab navigation reworked.** Refactored `Canvas` + `Base.onKeyTab` from the old `firstTab`/`nextTab` pair into a full `tabList: Base[]` rebuilt every layout pass. Tab now does an `indexOf` + `±1 mod len` walk; **Shift+Tab now goes backward** (the old code never read `canvas.isShiftDown()` and always advanced via `nextTab`). Outside any boundary (free-floating controls under the canvas) the cycle excludes anything that already belongs to a docked region or window.

**Buttons + checks + radios are tabable + keyboard-active by default.** `Button` constructor now sets `setKeyboardInputEnabled(true)` + `setTabable(true)` (was previously false — modern web a11y expectation).
