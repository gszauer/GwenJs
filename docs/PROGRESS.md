## 2026-04-27 — Keyboard-nav overhaul + Properties grid rebuilt against GWEN

**Tab navigation reworked.** Refactored `Canvas` + `Base.onKeyTab` from the old `firstTab`/`nextTab` pair into a full `tabList: Base[]` rebuilt every layout pass. Tab now does an `indexOf` + `±1 mod len` walk; **Shift+Tab now goes backward** (the old code never read `canvas.isShiftDown()` and always advanced via `nextTab`). Added a `_tabBoundary` field on `Base` with `setTabBoundary(b)` / `isTabBoundary()` plus two module-level helpers (`findTabScope`, `isWithinTabScope`) that walk the parent chain. `WindowControl`, `Modal`, `DockBase` (each docked region), and every `TabControl` page now mark themselves boundaries — Tab cycles within the nearest boundary instead of leaking into siblings. Outside any boundary (free-floating controls under the canvas) the cycle excludes anything that already belongs to a docked region or window.

**Buttons + checks + radios are tabable + keyboard-active by default.** `Button` constructor now sets `setKeyboardInputEnabled(true)` + `setTabable(true)` (was previously false — modern web a11y expectation). Space / Enter on a focused button fires `onPress`; on a `CheckBox` it toggles; on a `RadioButton` it selects (and refuses to deselect via `allowUncheck()`). Subclasses that genuinely shouldn't take focus — `MenuItem`, `ListBoxRow`, `TabButton`, `WindowCloseButton`/`Maximize`/`Minimize`, `CategoryButton`, the `ToggleButton` and `TreeNodeText` inside `TreeNode`, `NumericUpDownButton_Up`/`Down`, the inner radio + label inside `LabeledRadioButton`, and LRBs added via `RadioButtonController` — opt out with their own `setTabable(false)` calls.

**Arrow-key nav added to list-style containers.** `ListBox` (Up/Down move selection, Home/End jump, with auto-scroll-into-view that adjusts the vertical scrollbar), `RadioButtonController` (Up/Down/Left/Right cycle wrapping), `TabControl` (Left/Right + Up/Down switch tabs, Home/End jump; custom `renderFocus` draws the focus ring around the active `TabButton` instead of the whole control), `TreeControl` (Up/Down through DFS-flattened visible nodes; Left collapses or jumps to parent; Right expands or descends to first child; Home/End jump). Each container is itself the single tab stop — its rows/options/pages stay non-tabable.

**Slider visual overhaul.** Track-aligned focus ring (5 px tall — matching the notch tick height — centred on the slider, extended 3 px past each side) replaces the old full-perimeter ring that overlapped the nib. Drawing past the slider's bounds is safe because `Base.renderRecursive` restores the parent's clip region before calling `renderFocus`. Notched sliders (`setClampToNotches(true)`) now visually snap on every drag tick: `Slider.onMoved` calls a new abstract `snapBarToValue()` after `setFloatValue`, because `setFloatValue` short-circuits when the snapped value didn't change (no `invalidate` → no layout → bar stays where the Dragger last moved it). Without the eager snap, dragging within an already-current notch's snap zone left the bar walking around freely.

**Properties grid rebuilt against GWEN.** Multiple bugs traced to `PropertyTree.add` skipping `node.dock(Pos.Top)` (so PropertyTreeNodes stayed at Base's 10×10 default), and to our `TreeNode` not setting `m_InnerPanel` like GWEN does — children added with `new X(node)` landed directly on the node instead of routing into `_innerPanelChildren`, which meant `_innerPanelChildren.children.length === 0` and `TreeNode.layout` hid the toggle button. Added `enableInnerPanelRouting()` opt-in (registering the routing on the base class itself broke `TreeControl`, which constructs its `ScrollControl` as a child of `this` BEFORE its own `setInnerPanel(scrollControl)` runs — the scroll would land in the hidden `_innerPanelChildren` and the whole tree would vanish). `PropertyTreeNode` opts in. `Properties` gained a `postLayout` calling `sizeToChildren(false, true)` so a Properties grid docked Top inside a node fits its rows instead of clipping at 10 px tall; the splitter is excluded from the size tally via `doNotIncludeInSize()`. `Properties.addRow(name, prop, value='')` matches GWEN's 3-arg `Add` so the `setPropertyValue(value, true)` call fires `onChange` (which `PropertyColorSelector.updateSwatch` listens for to repaint its red square). Moved `ColourButton` from inside the `TextBox` to a sibling — the TextBox's 4×2 text padding was crushing the swatch to ~10 px tall. New **`PropertyNumeric`** editor wraps `NumericUpDown` (canonical value is the integer-as-string, exposes `getNumericUpDown()` for min/max). Demo's Properties panel now mirrors GWEN UnitTest: standalone grid on the left, PropertyTree with rich editors (Checkbox, ColorSelector, Numeric stepper, ComboBox) on the right, and an Item Three with 12 extra rows so expanding the tree exercises the vertical scrollbar.

**Bundle: `dist/gwen.min.js` = 199 KB raw / 49 KB gzip. Full suite: 1624/1624 green on desktop + mobile across 63 spec files.** Documentation updated: `docs/agent_docs.md` gains the `PropertyNumeric` row, fixes the broken Properties cookbook example (`addRow(name, prop, value)` rather than the non-existent `add(name, prop, value)`), and documents tab scoping + arrow-key nav under Common Gotchas. `docs/documentation.md` gets a new "9. Keyboard navigation" section.

## 2026-04-27 — Bug-fix sweep: tree control, multi-line text, drag-and-drop, window chrome

**Tree control rebuilt against GWEN's TreeNode.cpp.** The previous port had several silent deviations: nested children's `onNamePress` was never wired to the TreeControl (so click-to-select only deselected siblings at the SAME depth — "one selection per level" bug); `TreeControl.deselectAll` inherited from TreeNode iterated `_innerPanelChildren` (the unused base field, not the scroll-hosted real children); the [+]/[-] glyph was painted at the top-left 9×9 of its 15×15 atlas cell, leaving the visible art shifted up-and-left by 3px; the toggle button's onPress only flipped its own `_open` flag instead of calling the parent's `toggle()`; selected rows had their text covered by the opaque blue Selection rect because `drawTreeNode` was called from `renderOver` (after children) instead of `render` (before children); top-level nodes drew a spurious horizontal connector to the left of their title because `setRoot(true)` wasn't being called in `TreeControl.addNode`. Added a `_treeControl` field on TreeNode with `setTreeControl/getTreeControl`, propagation in `TreeNode.addNode`, and a `TreeControl.onNodeAdded` hook that subscribes the tree to every node's `onNamePress` regardless of depth. Override `getChildNodes`/`deselectAll`/`expandAll` on TreeControl to iterate the actual scroll-hosted nodes. Added a `TreeNodeText` Button subclass that updates text color per-render based on toggle state (matches GWEN's `TreeNodeText::UpdateColours` — selected rows use `tree.selected` against the blue background). Centred the painted [+]/[-] glyph inside the 15×15 atlas cell. Strict toggle-button vertical centering against the title row. ToggleButton suppresses its focus ring (matches GWEN).

**TextBox / TextBoxMultiline / PasswordTextBox audit.** `TextBoxMultiline` was rendering "all on one line" because `Text.refreshSizeWrap` tokenised by `\s+` and lumped `\n` in with regular whitespace — hard newlines never forced a break. Split the wrap algorithm to scan for `\n` first and word-wrap each segment independently. The Label's inner `Text` was also stuck at its constructor-default 10×10 bounds because nothing synced its width to the Label's interior — `refreshSizeWrap` reads `this.width()` for the line-break constraint, so wrap output was useless. Label now syncs the inner Text's bounds in `postLayout` + `onBoundsChanged` whenever wrap is enabled. The multi-line caret was the full textbox height and X-positioned via the entire string's prefix (so a click on visual line 3 hit-tested as "end of line 1"); `TextBoxMultiline` now overrides `renderOver` with hard-newline-aware caret + selection drawing (caret = one font line height, selection handles single + multi-line spans), and `charIndexAt` accepts an optional `localY` to pick the line first then scan that line's prefixes only. `makeCaretVisible` early-returns in wrap mode (long lines wrap rather than scroll, so no `_textOffsetX` is ever needed). PasswordTextBox's caret hit-test and renderOver measured against the unmasked real text — when the mask glyph's width differs from the underlying characters' widths, the caret drifted off the visible glyphs (most obvious as "extra trailing space" past the last `*`). Added a `protected displayedText()` hook on TextBox that defaults to `getText()`; PasswordTextBox overrides to return `'*'.repeat(realText.length)`. The three measurement sites (`makeCaretVisible`, `charIndexAt`, `renderOver`) all read from `displayedText()`. Descender clipping fixed at the source: `FontAtlas.measureText` was returning `realsize` (em-square, stops at the alphabetic baseline), so labels sized to it clipped 'g'/'y'/'q'/'p'. Added a `lineHeight` field on the per-font handle populated lazily in `ensureFont` from `ctx.measureText('Ag').fontBoundingBoxAscent + Descent`; `measureText` returns it.

**Drag-and-drop fixes.** Fixed several issues that broke the docking demo: (1) `Canvas.renderDragPreview` computed shift as `target - dc.localPosToCanvas({0,0})` (which walks the entire ancestor chain), but `dc.doRender` only adds `dc._bounds` to the renderer offset — the ghost was offset by the sum of all ancestor positions. Fix: `target - dc.x()/dc.y()`. (2) Hovering during a drag fired `onMouseEnter`/`onMouseLeave` on whatever sat under the cursor — list rows, menu items, file-menu buttons — making them visibly highlight as the user looked for a drop target. Self-guarded `Canvas.updateHoveredControl` to early-return when `dragStarted`, and clear `hoveredControl` at drag start. (3) `inputMouseMoved` skipping hover dispatch during drag killed the redraw loop (no Enter/Leave → no `redraw()` calls → renderCanvas short-circuited on `!_needsRedraw`); now calls `this.redraw()` explicitly inside the drag branch so the ghost follows the cursor. (4) `inputMouseButton` had a `!hovered` early-return that ate the mouse-up during drag (since we cleared hoveredControl) — drop never fired. Added a drag-release short-circuit at the top of `inputMouseButton`. (5) `setupChildDock` used the constructor-default 200×200 size for the new child DockBase, which overflowed when dropping on the top/bottom of a 150px-tall output strip — `bh -= 200` went negative, the existing fill control collapsed, and the new child's title bar / resizer spilled outside the host's render bounds and got clipped. New children are now sized to half the host's relevant dimension before docking. (6) Splitting one tab off a two-tab dock left the source still showing a tab strip with a lone tab — `attachTabButtonTo` and `attachTabButton` both called `target.invalidate()` but not `sourceTC.invalidate()`, and `Base.invalidate()` doesn't walk up. Now both call `sourceTC.invalidate()` so its `setHidden(tabCount() <= 1)` rerun on the next layout pass. (7) Drag source is now hidden via `setHidden(true)` (instead of a render-only suppress flag) so the layout reflows around the now-empty slot — for `TabWindowMove` we hide the parent DockBase, for other packages the drawcontrol itself.

**Window chrome.** Title bar was a 24px Dragger + 4px bottom margin against a 32px painted title strip with a baked 1px separator — left an empty band below the dragger and a horizontal line spanning the whole window. Now: 28px dragger, no bottom margin, atlas `Window.Normal/Inactive` margin updated to `[8, 28, 8, 8]`, painter draws a 28-row title gradient with no separator, title text vertically centred. Close button: skin was hardcoding a 31×31 destination rect from the 31×31 atlas glyph, so a button living in a 22-px-tall title bar lost its bottom edge. The three window-button draws now use `ctrl.getRenderBounds()` and let the texture scale into whatever bounds the host chose; WindowControl sizes the close button 24×24 with 2px top/bottom inset. Modal overlay's `BAKED_ROW_508` `ModalBackground` entry was opaque `#191919` — `parseHex` decoded that as fully opaque, so the modal blacked the screen out. Changed to `'rgba(25,25,25,0.40)'` for a proper translucent overlay.

**Texture sampling bleed.** Outer-edge LINEAR sampling at 9-slice region boundaries blended in the unpainted (transparent) texel just outside, producing a white smear on the file menu's left and a darker smear on its right (and the same class of bleed on every bordered region). `Skin.drawBordered` / `drawSingle` / `drawSingleCentered` now apply a half-texel UV inset so the leftmost/rightmost destination pixels snap to the centres of the in-region texels. `Menu.Strip` gets a custom `drawMenuStrip` (solid filled rects rather than a 9-slice) — the bevel column at `x+1` would otherwise smear horizontally regardless of the chosen margin. `CategoryList.Inner`'s painter moved the dark blue separator from row `y+21` (first row of the 9-slice center patch) to row `y+19` (inside the top patch) so vertical stretching of the center can no longer smear the line down into the body of the expanded "Controls" list.

**Demo polish.** `showDemo` now drives the sidebar selection too, so the default-open demo (`Button`) starts highlighted in the CollapsibleList. Window demo's "Normal Window" / "Modal Window" buttons centred via a `CenteredColumn` Base subclass that recomputes child x positions on every layout pass. TreeControl demo gets 7 extra `Branch N` nodes with sub-branches so the vertical scrollbar gets exercised. Pre-opened "Window 1" reordered before the centering column so the WindowControl ends up later in `_children` and renders + hit-tests above the layout-only column. `LabelMultiline` placeholder text replaced with lorem ipsum. **Bundle: `dist/gwen.min.js` = 191 KB raw / 47 KB gzipped. Full suite: 1624/1624 green on desktop + mobile.**

## 2026-04-26 — Stub sweep: tooltip, accelerators, word-wrap, drag preview, caret scroll

**Re-dock-back bug:** dragging a tab off a dock then back to the same edge left the inner page hidden. Root cause: the source TabControl's `_currentButton` ref still pointed at the moved tab, so `attachTabButton`'s `if (!getCurrentButton()) handleTabPress(btn)` short-circuited and the page never got `show()`n. Fix: also call `handleTabPress` when the cached current button is no longer a child of our strip (i.e. the ref is stale) or when it's the very tab being re-attached. Same fix mirrored into `DockBase.attachTabButtonTo` via a new public `DockedTabControl.onTabPressedExt`.

**Stub/TODO sweep, finishing what was deferred:**
- **Tooltips actually render now.** `Label.setToolTip` overrides `Base.setToolTip` to build a real text-bearing `Label` (also setting its `name` to the text so existing tests keep passing). `Canvas.renderCanvas` now calls `renderToolTip()`, which positions the hovered control's tooltip near the cursor (clamping to canvas bounds), reveals it briefly, draws via `skin.drawToolTip`, and re-hides so it never participates in layout/hit-test.
- **Drag preview** renders via `Canvas.renderDragPreview` — when a drag is active, the renderer offset is shifted so the package's `drawcontrol` paints at the pointer minus the recorded `holdoffset`, then restored. Provides the visual feedback GWEN's DragAndDrop manager draws.

## 2026-04-26 — DockBase wired into demo + scrollbar drag clamp + drag-and-drop dispatch

**Demo now uses the headline DockBase feature.** The sidebar (CollapsibleList) and Output log are no longer docked directly to the canvas; they live as tabs inside a `DockBase` whose left and bottom edges hold `DockedTabControl` panels. Each docked tab has a title bar showing its name, a resizer on its inside edge for live width/height adjustment, and accepts dragged tab buttons from any other dock — drop a tab onto a different edge to reparent it (matches GWEN UnitTest's behaviour). `MenuStrip` and `StatusBar` remain canvas-level since they're chrome, not content.

**Drag-and-drop dispatch wired up.** The DockBase structure was already in place but the actual D&D *input router* was a TODO stub in `Base.ts` — `dragAndDrop_StartDragging` set `drawcontrol = this` but nothing tracked pointer movement, dispatched HoverEnter/Hover/HoverLeave to potential drop targets, or fired HandleDrop on release. Implemented the dispatch in `Canvas.inputMouseMoved` / `inputMouseButton`: a left-press over a draggable control becomes a candidate, the candidate promotes to an active drag once the pointer moves past `DRAG_START_THRESHOLD = 5px`, then on each subsequent move the canvas hit-tests for the deepest control whose `dragAndDrop_CanAcceptPackage` returns true (walking up the parent chain so a drop onto a tab-strip child still finds the host DockBase) and dispatches HoverEnter/HoverLeave/Hover. Release calls HandleDrop on the current target. `TabButton` registers package `"TabButtonMove"` in its constructor; `TabTitleBar` registers `"TabWindowMove"` and overrides `dragAndDrop_StartDragging` so `drawcontrol` points at its parent `DockedTabControl`. After a tab moves, both `DockBase.attachTabButtonTo` and `DockedTabControl.moveTabsTo` now emit `onLoseTab` on the source TabControl so its owning DockBase runs the redundancy/consolidation pass and hides the now-empty source dock.

**`ScrollBarBar` drag clamp fix:** the thumb's `restrictToParent=true` was clamping against the *full* scrollbar bounds (including the up/down or left/right arrow buttons), so dragging would slide the thumb *under* a button. Override `moveTo` to clamp instead to the track area between the buttons (using the parent ScrollBar's `width()`/`height()` to size the buttons). **Visual baselines regenerated; full suite 1624/1624 green.**
